# Expo SDK is pinned to 54 — do not upgrade without asking

The project was scaffolded on SDK 57 but was rolled back to **SDK 54** because the Expo Go app on the Play/App Store lags behind the latest SDK (Apple review delays especially) and can't open newer-SDK projects. Bump back up only once Expo Go in the stores has caught up, or once you're fully off Expo Go and building exclusively via EAS dev-client. Read the versioned docs at https://docs.expo.dev/versions/v54.0.0/ before writing code that depends on SDK-specific APIs.

# Beggars Map

Crowdsourced map/directory of cheap eats in Bengaluru (India take on Korea's viral "Geoji Map" / 거지맵). **₹100 price cap** — listings must be ₹100 or under, sort cheapest-first, community upvotes surface quality. (Decision changed 2026-08-25: originally "no cap," the user revised this to match Geoji Map's own hard cap — see full product plan and prior locked decisions in Claude's memory `project-beggars-map`, but this price-cap change supersedes what's written there.) **User-facing copy says "Affordable Eats," not "Cheap Eats"** (changed in a later pass, across web's `<title>`, meta description, tagline, and error/legal copy) — "cheap eats" above is describing the product genre for this doc's own purposes, not a literal string to match; don't revert the UI copy back to "cheap" based on this file's own wording.

**Two independent apps, one Supabase backend:** a React Native mobile app (repo root, `src/`) and a Vite/React web app (`web/`). They diverge more than a typical "shared backend, thin client differences" setup — see Auth below in particular, where mobile requires sign-in and web is anonymous-only by design.

**Web app status:** built and live at `beggarsmap.com` (Vite + React, deployed on Vercel — see memory `project_launch_status` for domain/hosting detail), solving the original app-only zero-friction-access gap vs. the Korean original. Mobile is dev-client only so far — no store listing yet (see Launch status below).

**Price cap implementation status:** enforced end-to-end — DB constraint via `0004_price_cap.sql` (`price_rupees > 0 and price_rupees <= 100`), plus client-side validation in both `AddListingScreen.tsx` (mobile) and `AddListingModal.tsx` (web). The `0003_seed_demo_listings.sql` seed data was also brought under the cap (one demo listing was ₹180) since it runs before `0004` and would otherwise break that migration on a fresh `supabase db reset`.

## Stack
- Expo (React Native) + TypeScript, SDK 54, `blank-typescript` template, mobile only
- Web: Vite + React + TypeScript (`web/`), no router — single `App.tsx` with modal-driven navigation (Add Listing, Listing Detail, Legal all render as modals over the map, not separate routes)
- Navigation (mobile, `src/navigation/`) — root stack (`Tabs`, `ListingDetail`, `AddListing`, `PickLocation`, `SignIn`, `Legal`) wrapping a bottom tab navigator (`Map`, `Contribute`, `Leaderboard`, `Profile`). The `Contribute` tab never renders its own screen — its `tabPress` is intercepted and redirected to `AddListing`/`SignIn` on the root stack, so it needs `Map` to stay in the tab bar as the way back (don't remove `Map` from the tab bar without restoring another path back to it).
- Map (native/mobile only — see below for web, which uses Google Maps instead): OLA Maps (India-tuned, dedicated key in `EXPO_PUBLIC_OLA_MAPS_API_KEY`, not shared with RentalIntel's key — see budget note below). Layers:
  - **Interactive map** (`src/components/ListingsMap.tsx`, used on the Map screen; `src/screens/PickLocationScreen.tsx`, used for manual pin placement in Add Listing): `@maplibre/maplibre-react-native` pointed at OLA's vector tile style JSON (`vectorStyleUrl()` in `src/lib/olaMaps.ts`). **Native module — will not run in Expo Go.** Requires an EAS dev-client build, already set up (`eas.json`, EAS project linked under `nikhil_sinha/BeggarsMap`) — rebuild via `npx eas-cli build --profile development --platform android` only when a *native* dependency changes; pure JS/TS changes just need a Metro reload, no rebuild.
  - OLA's style JSON references tile/sprite/glyph URLs that don't carry the API key themselves — `src/lib/olaMaps.ts` registers a `TransformRequestManager.addUrlSearchParam` transform at module load to append `api_key` to every request to `api.olamaps.io`. If you see 401s on sources/sprites/glyphs, this is the first thing to check.
  - Markers use `anchor="bottom"` (pin tip points at the coordinate) — the default `"center"` anchor caused pins to visually overflow their container.
  - **Static map fallback** (`staticMapUrl()` in `src/lib/olaMaps.ts`): plain `<Image>` hitting OLA's static-map REST endpoint, no native module needed — works in Expo Go. Superseded by the interactive map on the Map screen but kept as a lightweight-preview helper.
  - **Places search** (`searchPlaces()` in `src/lib/olaMaps.ts`): OLA's autocomplete endpoint, used from both `MapScreen.tsx` (landmark search that flies the camera) and `PickLocationScreen.tsx` — each screen independently debounces its own call to this function and drives its own camera `flyTo`; this is duplicated per-screen logic (not a shared hook), a known tech-debt item, not a functional bug.
  - No in-app turn-by-turn navigation. Listing Detail's "Directions" button hands off to the device's Google Maps / Apple Maps app instead (same pattern as Zomato/Swiggy).
  - **Scaling risk**: if this goes viral, OLA's free tier (500K loads/month) is the first thing to break — well before Supabase's free-tier limits. Upgrading is just a paid-plan flip, no code change, but budget for it if growth is real.
- Map (web only, `web/`): **hybrid** — Google Maps JS API renders the map, OLA Places handles search. Rendering migrated off MapLibre 2026-08-28: `web/src/lib/googleMaps.ts` loads the JS API via Google's official inline dynamic-import bootstrap snippet (not an npm loader package — `google.maps.importLibrary('maps'|'marker')`), keyed by `VITE_GOOGLE_MAPS_API_KEY`. `web/src/components/MapView.tsx` renders the map and `AdvancedMarkerElement` pins (needs `VITE_GOOGLE_MAPS_MAP_ID` — a Map ID created in Cloud Console, separate from the API key). **Place search reverted to OLA Places 2026-08-28** (same day): Google Places API (New) was tried first but its per-request billing (Autocomplete + Place Details Essentials SKUs, ~$0.85–1.50/1000 in India after a 70k/month free quota per SKU) looked expensive for a search box that also does local listing-name filtering, so `web/src/lib/olaPlaces.ts` (search-only — no map-tile responsibilities, unlike the old pre-migration `olaMaps.ts` this was revived from and which is now deleted) does `searchPlaces()` against `api.olamaps.io/places/v1/autocomplete`, free tier, keyed by `VITE_OLA_MAPS_API_KEY` (yes, both a Google key and an OLA key are configured for web — normal for this hybrid, not a leftover). `App.tsx`'s home search box only fires the external OLA call when the query has **zero local listing matches** (`filtered.length === 0`) — normal typing that matches an existing listing never reaches OLA at all. Forward geocoding was never needed on web: Google Maps share-link parsing (`googleMapsLink.ts`) extracts lat/lng from the URL itself, no API call. **Reverse geocoding is back, in a different shape than before**: it was fully removed for a few passes (the old `web/src/lib/geocoding.ts`, Nominatim/OSM, was deleted with nothing replacing it), but a later pass reintroduced it via `web/src/lib/reverseGeocode.ts` — OLA's `/places/v1/reverse-geocode` endpoint (same key as forward search, confirmed live/working against a real coordinate, not a documented-but-unverified guess), called **once at Add Listing submission time**, not live per-view — see "Human-readable location" below. Web's listing popup shows this stored descriptor when present; it does not do a live geocode lookup on every view the way native mobile's `ListingDetailScreen.tsx` still does with its own separate Nominatim call (that native code path is untouched and intentionally still independent).
  - **The selected-listing popup is no longer a Google `InfoWindow`** (changed a previous pass). `InfoWindow` content renders inside Google's own nested map panes, which bundle the base map tiles and every overlay under one shared stacking rank from any *sibling* element's point of view (`.list-panel-outer`, the restaurant list) — empirically, no z-index could put an `InfoWindow` above the side panel without the base map tiles also winning, breaking the "panel floats over the map" look. `MapView.tsx` now positions its own plain `.map-popup-anchor`/`.map-popup-card` divs by directly measuring the selected pin's own DOM element (`selectedMarkerElRef`, via `getBoundingClientRect()` on a `requestAnimationFrame` loop while a popup is open) rather than Google's Projection API, which proved unreliable for this (empirically returned near-`(0,0)` for real coordinates in testing, independent of raster/vector rendering mode). **This popup is exactly pin-anchored, with no boundary clamp — this changed from an earlier pass and should not be reintroduced.** An earlier version clamped the computed x/y against the container edges and the list panel's bounds (a top floor, a bottom ceiling derived from the mobile sheet height, left/right floors derived from the list panel's width) so the card could never render off-screen or underneath the list panel. That clamp was removed: it silently substituted a *different* on-screen position than the pin's own real coordinate whenever a selected pin sat near an edge, which reads as the popup having detached from its listing's actual location — exactly the bug report that triggered removing it. The popup's anchor now always equals `pinRect.left + pinRect.width/2, pinRect.top`, full stop, including near every edge. The trade-off this brings back (accepted, not a bug): a pin close enough to the list panel or another floating control can now render its popup partially underneath that control. **Which side wins that overlap is a z-index question, resolved via `.map-popup-anchor { z-index: 3 }` — deliberately *below* `.list-panel-outer`'s original, unchanged `z-index: 4`** — so the list panel (the primary, always-present browsing surface) stays fully visible and fully clickable wherever it overlaps the popup. The other floating controls (search bar, zoom/locate buttons, the picking-location dialog, the exit toast — `z-index: 5–8`) are unrelated to this and unchanged; they still correctly render above the popup, same as always. **If this needs touching again: don't raise `.list-panel-outer`'s z-index to fix a popup-vs-list overlap.** z-index is a strict total order — raising the list panel above the popup necessarily also raises it above everything else that was already above it. Confirmed by testing: doing this once broke the picking-location dialog's own confirm button, since the dialog's `z-index: 6` no longer beat the list panel. Lowering the popup below the list panel's own unchanged value is the only change that doesn't cascade into unrelated relationships. This popup is shared by every breakpoint, mobile portrait included (see the "Web mobile portrait only" bullet below for why that's a change).
  - **A separate, now-fixed root cause used to make the popup visibly drift even with exact-anchor math correct on paper**: `MapView.tsx`'s marker-rebuild `useEffect` used to depend on the `onSelectListing` callback prop directly. `App.tsx` never wrapped `selectListing` in `useCallback` (unlike `onMapClick`, which already used a stable ref for exactly this reason), so that prop got a brand-new function identity on *every* render of `App` — typing in search, a sheet-drag `pointermove`, a `ResizeObserver` tick, anything. Each of those unrelated renders tore down and rebuilt every marker on the map (the effect's dependency changed, so it re-ran). While the selected marker's DOM element briefly didn't exist mid-rebuild, the popup-position RAF loop found nothing to measure and kept rendering at its last-known position — which is what actually produced the visible drift, independent of whatever the clamp was or wasn't doing. Fixed the same way `onMapClick` already was: `onSelectListingRef` (a ref, synced via its own effect, read inside the marker click handler) replaced the direct prop in the rebuild effect's dependency array. If a future change reintroduces an unstable callback prop into that effect's deps, this exact symptom (popup silently freezing mid-interaction) will come back.

Requires **"Anonymous sign-ins" enabled** in the target Supabase project's Auth settings (dashboard toggle only, no CLI/API way to check or flip it remotely) — as of the last verified check this had been **off** on the production project; confirm it's on before assuming web writes work live.   - **Local Supabase: safe reset/backup procedure.** `supabase db reset` (any target) drops and fully recreates the database from `supabase/migrations/*.sql` — anything not produced by a migration (every app-created listing, review, vote, report, and any locally-created auth user) is permanently deleted, with no built-in way to get it back. This already happened once: a developer-added listing was lost this way on 2026-08-30. Treat that as a standing warning, not a one-off.

    - Needing a genuinely clean from-scratch local DB: `npm run db:reset:safe` — the only sanctioned path. It warns, requires typed confirmation (`RESET`) unless run with `--yes`, backs up via `npm run db:backup`, verifies the backup, resets, clears the fresh reseed, and restores your data automatically (`scripts/safe-reset-local-db.mjs`). Never run `supabase db reset --local` on its own.
    - Manual backup/restore: `npm run db:backup` writes a verified, data-only dump to `supabase/backups/<timestamp>.sql` (gitignored); `npm run db:restore -- <path>` restores it (defaults to the newest file in that folder). 13. **Search is a local relevance search for the listing list, and an independent OLA search for the suggestion dropdown — the two run together and never suppress each other (web only).** This replaced an earlier design (search-bias fix, then a full pipeline rework, then a "local match wins outright, no OLA call at all" design) after a string of real production bugs, the most recent being: typing "dosa" (which matches several listings' notes/names) never showed any OLA suggestion at all, because the old debounce effect skipped the OLA fetch entirely whenever a local match existed — meaning a real, addable place named similarly to an existing listing could never surface. Current design, in order:
    - **Local relevance match** (`App.tsx`'s `textRelevance`/`textMatches`) checks `name`, `note`, *and* `location_label`, case-insensitive substring — plain `includes()`/`startsWith()` already gives free partial-input support ("nort" matches "north indian", "dos" matches "dosa") with no separate fuzzy-matching library. Ranked into tiers — name-starts-with (4) > name-contains (3) > location_label-contains (2) > note-contains (1) — so a listing actually named for the query always outranks one that merely mentions it in passing; ties within a tier break by distance-to-viewer (if geolocation is known) or newest-first otherwise. A local match still wins the *listing list* outright (`filtered` uses `textMatches` before ever falling back to area matches) — that part is unchanged.
    - **OLA is now called for every non-empty query, local match or not** — the debounce effect's old `if (textMatches.length > 0) return` early-exit (which skipped the OLA fetch, and with it the whole suggestion dropdown, whenever a local match existed) is gone. `executeSearch()` (Enter/the icon) mirrors this: it now always awaits `resolveAreaMatches()` first, regardless of whether a local match is about to win the camera focus. Still exactly one debounced OLA call per typing pause (and one per execute) — this isn't a second pipeline, just no longer gated on `textMatches` being empty.
    - **`resolveAreaMatches()` picks the OLA prediction whose *name* best matches the query, not `results[0]`.** OLA's autocomplete ranks predictions mostly by proximity to the bias point, not by name relevance — confirmed live: searching "Juicy Spot" biased near Bengaluru center returned an unrelated street address as prediction #1, with the actual "Juicy SPOT" restaurant only at #2, which fed the wrong point into the area-match radius check below. `bestPlaceMatch()` (`web/src/lib/olaPlaces.ts`, duplicated from — not shared with — `supabase/functions/resolve-maps-link/index.ts`'s own function of the same name and approach, same reasoning as the existing per-platform content-moderation duplication) scores every prediction by a sliding-window Levenshtein similarity against the query text and picks the best one, falling back to `results[0]` only when nothing clears a 0.4 similarity bar.
    - **Area/locality resolution — the resolved center becomes the radius-search point regardless of whether OLA suggestions are also shown**: the point becomes the center of a 3km radius search (`AREA_MATCH_RADIUS_KM`) against our own listings, ranked nearest-to-*that-point*-first (a different "nearest" than the text-match tiebreak above, which is nearest-to-*viewer*). If any of our own listings are nearby, those are what the map/list show — OLA's own predictions are never presented as if they were Beggars Map listings, only as the separate suggestion dropdown and the "add this place" pin flow described next.
    - **Any place OLA resolves gets a visible search pin and the camera moves to it, even while the user is still typing (not just after Enter) — regardless of whether Beggars Map listings also happen to be nearby.** This is `searchPin`, set from the exact same `center`/place value `resolveAreaMatches()` (or `selectSearchResult`) resolved, across the debounce effect, `executeSearch()`, and `selectSearchResult()` alike — one authoritative coordinate feeding the pin, the camera, and (via `areaCenter`) Add Listing's initial location. **This used to also require `nearby.length === 0`** (only pin/focus a "genuinely novel place" with nothing of ours nearby), which is what originally fixed "Tandoori Taal - Palace Road" showing the empty state with no pin anywhere. That extra condition turned into a silent, code-change-free regression as the listing set grew: `bestPlaceMatch` kept resolving that exact query to the same correct coordinate every time, but the moment any unrelated listing landed within `AREA_MATCH_RADIUS_KM` of it, the pin/camera-focus for that correctly-resolved place stopped appearing again — confirmed live by re-running the same four searches ("Tandoori Taal - Palace Road", "Whitefield", "Juicy Spot", "Meghana Foods Indiranagar") through a real browser with the full pipeline logged end-to-end: 3 of 4 had `nearby.length > 0` and were silently getting their pin suppressed even though the resolved coordinate was correct every time. Fixed by dropping the `nearby.length === 0` condition — a resolved place now always gets pinned/focused unless a local text match already won outright (`textMatches.length === 0` is still checked), with nearby Beggars Map listings folded into the *same* camera bounds (`focusMapOn([...nearby, center])`) instead of replacing the pin. This is still the one deliberate exception to "camera movement stays reserved for an explicit search" during live typing — it's just no longer narrowed to the "nothing else nearby" sub-case, since that sub-case was the actual bug.
    - **A debounced-but-not-yet-resolved query no longer shows the "no listings match" empty state.** `searching` (`App.tsx`) is true from the moment a keystroke invalidates the previous query's `areaListings`/`areaCenter` until the debounced `resolveAreaMatches()` call actually resolves. Before this existed, that empty state (and its clickable "add it to the map" button) rendered instantly on every keystroke — since `areaListings`/`areaCenter` are reset synchronously, well before the 400ms debounce timer plus however long the OLA fetch itself takes — so clicking the button inside that ~600-900ms window opened Add Listing with no location, because `areaCenter` genuinely hadn't resolved yet. The list panel shows "Searching…" instead while `searching` is true.
    - **"Add it to the map" (the empty-state button) carries the resolved coordinate straight into Add Listing — the user never has to search the location twice.** `addSearchedPlace()` seeds `AddListingModal`'s `initialCoords` from `areaCenter`, the exact same value `searchPin`/the map pin were set from, so the pin the user just saw on the map and the location Add Listing opens with are guaranteed to be the same coordinate, not two independently-computed ones. `areaCenter` is `null` when nothing resolved (a genuinely unknown query) — the modal just opens with no pre-filled location then, same as before this fix, and every manual location option (current-location, pick-on-map, paste-link, the ✕ clear-pin control) still works exactly as it did.
    - **Picking a dropdown suggestion must not let the very next render wipe out what it just set.** `selectSearchResult()` calls `setQuery(place.name)`, which re-triggers the debounce effect (it depends on `query`); that effect's `skipNextSearchRef` flag exists specifically to let a programmatic query change skip re-fetching, but the effect used to reset `areaListings`/`areaCenter` to empty/null *before* even checking that flag — silently undoing the exact values `selectSearchResult()` had just set moments earlier in the same update. Confirmed live: picking a suggestion set `areaCenter` correctly, then this effect's own reset cleared it back to `null` before the user could click "add it to the map," which is why that flow opened Add Listing with no location. Fixed by checking `skipNextSearchRef.current` before the reset, not after.
    - **Enter, the search icon, and picking a dropdown suggestion all converge on this same pipeline** (`executeSearch()` for the first two; `selectSearchResult()` treats the picked place as the geographic center and runs the identical nearby-lookup, using that exact suggestion's own coordinates — never `results[0]` or a separately-recomputed value). The debounced 400ms auto-search effect that fires while typing shares the same underlying pipeline; per the point above, it now moves the camera whenever a place resolves and no local text match already won, not just the narrower "nothing else nearby" case — an ordinary query that already has a *local* match still can't jump the view around mid-keystroke, since that check happens first and short-circuits the rest.
    - **The dropdown always closes once a search is explicitly executed** (Enter, the icon, or picking a suggestion), even in the one case where OLA still has "add this place" suggestions worth keeping around (`placeResults` stays populated for that, just not shown as an open dropdown) — leaving it open after an explicit execute used to read as the search not having finished.
    - **Map camera**: a `searchFocus` prop/effect on `MapView.tsx`, entirely separate from `flyToCenter` (still used, unchanged, by listing-selection and location-picking) and untouched by the popup-anchoring code. One result point pans+zooms there; several fit the camera to bounds containing all of them (always via `fitBounds`, including the single-point case — a zero-area bounds — rather than a separate `panTo` special-case, so both share the same padding and the same over-zoom guard clamping to 15). **Padding is an asymmetric object** (`{ top: 100, right: 380, bottom: 60, left: 60 }`), not a flat number — a flat number pads every side equally, which isn't enough to keep a fitted point clear of the app's own floating chrome on top of the map itself: the search bar (top) and, on desktop/tablet/landscape, the ~340-460px list panel (right). Confirmed live on production: a "dosa" search correctly computed bounds including all matches, but 2 of them rendered directly underneath the list panel/search bar — geographically "in view," visually invisible. The initial all-listings `fitBounds` on load still uses a flat `60` — same underlying class of issue, but out of scope for this pass since it wasn't the one reported broken.
    - **Result ordering in the list**: now baked directly into `filtered` itself (relevance+proximity for text matches, proximity-to-area-center for area matches) rather than a separate reorder — `desktopListListings` no longer exists; desktop/tablet/landscape use `filtered` directly. Mobile portrait's own always-on nearest/newest-first browse ordering (`mobileListListings`) is preserved for the no-query case, but no longer re-applied on top of `filtered` while a search is active, since that would silently undo the relevance ranking.
    - **Backing out of a search without picking anything**: an inline ✕ clear button (visible whenever the query is non-empty), Escape (same full clear), and the browser back button / edge-swipe all now fully reset the search (`clearSearch()` / the shared `resetToHome()`, both of which also clear the resolved `areaCenter`/`searchPin`). `hasOpenState` (the boolean that drives the app's one-history-entry-per-open-view mechanism) now includes "query is non-empty" as one more condition — typing the first character pushes one history entry the same way opening a modal does, and clearing back to empty consumes it the same way closing one does. This was a deliberate, explicit widening of what back/swipe closes — it used to stop at the search-results dropdown specifically because that felt too lightweight to be a "view"; it no longer does.
    - **The search bar's own width is one CSS custom property (`--search-bar-w`, set on `.map-frame`), read by both `.search-bar` and `.map-search-results` (the dropdown)** — not two independently-computed values. It used to be a flat `max-width: 68%` on desktop (ballooning to cover most of the map on a wide monitor) with the dropdown separately spanning the full overlay row (`right: 14px`) regardless of how wide the search bar actually was, so the dropdown visibly extended past the search bar's own right edge. Desktop/tablet now use `clamp(260px, 32vw, 440px)`; mobile breakpoints override the variable locally (full-row-width in portrait since the Add button moves to its own row there; a narrower `calc(100vw - Npx)`/`min(320px, calc(55vw - Npx))` in the shared-phone and landscape-phone rules respectively, sized to leave room for Add on a shared row) — **always as `vw`-relative `calc()` math, not a bare `%`**, because a `%` on `.search-bar` (a flex item, resolving against its flex container) and a `%` on `.map-search-results` (`position: absolute`, resolving against its own containing block) resolve against genuinely different reference boxes and quietly drift apart — confirmed live, up to 74px apart on some mobile widths. `vw` is always relative to the viewport regardless of which element uses it, which is what actually guarantees the two can never drift out of sync again.
14. **Double-swipe-down-to-exit (mobile web only)** — two fast, deliberate downward swipes on the bare map surface, only while `sheetState === 'map'` (the sheet collapsed to its peek zone) and nothing else open (`!hasOpenState`), hand off to `window.history.back()` — the closest a web page can get to closing its own tab, since `window.close()` only works on a tab the page itself opened via script. Always shows an on-screen message alongside the attempt, worded to be accurate regardless of whether `history.back()` actually leaves the site or is a same-document no-op — **deliberately not branched on `window.history.length`**: that value gets permanently inflated by one after the *first* modal open/close in a tab (the app's own `pushState`/`back()` pair recycles the same history slot on every later open/close, so it doesn't keep growing, but that first bump never reverses), so it can't reliably distinguish "there's a real page behind this" from "there's just our own leftover slot." Excluded targets (checked via `.closest()` on the touch's target element): `.list-panel-outer` (so this can never fire off an ordinary list pull-up/pull-down — a completely separate gesture, on a separate element, already using its own pointer handlers), `.map-overlay-row`, `.zoom-control`, `.locate-control`, `.map-search-results`, `.picking-dialog`. Also gated out entirely whenever `sheetState === 'list'` — "home" for this gesture specifically means MAP mode.
15. **Human-readable location (web only)** — `web/src/lib/reverseGeocode.ts` resolves a listing's picked coordinate into a short locality descriptor via OLA's `/places/v1/reverse-geocode` endpoint (same provider/key as forward search — deliberately not Google's Geocoding API, a separate billed SKU from the Maps JS API key already in use). **Prefers "Street, Area" when OLA's response has both** ("7th Main Road, Indiranagar") — more specific/useful than the area alone while still short, never a full postal address. Falls back to the area alone when that specific point's response has no street-level component at all (confirmed this genuinely happens — e.g. CTR's own coordinates resolve a `sublocality` but no `route`/`street_address`), then the street alone in the reverse case, then `locality` (city) only as a last resort — never state/country. Returns `null` — never a placeholder — the moment nothing in OLA's response supports even the last-resort case. Stored once on `listings.location_label` (`0010`) at Add Listing submission time, not re-resolved on every view. This format went through one earlier, briefly-shipped iteration that preferred the area alone as the default (with street+area only as a fallback) — reverted after feedback that the street-included form reads as more useful; if this area gets touched again, "Street, Area" first is the current, deliberate preference, not an oversight.
    - **Submission waits briefly for an in-flight lookup, but is never blocked indefinitely by one.** `AddListingModal.tsx`'s `submit()` awaits `resolveLocationLabel()`, which races the currently-in-flight `reverseGeocode()` promise (tracked via `locationPromiseRef`) against a 4-second timeout — a normal-latency OLA response has time to land before the insert fires (fixing an earlier, confirmed-live bug where listings were submitted with a permanently `null` label despite reverse geocoding succeeding for their exact coordinates, because the original code read `locationLabel` state synchronously with no wait at all), while a slow/hung request still can't stall submission past 4s. `reverseGeocode()` itself still wraps its fetch/parse/build logic in one `try/catch` that returns `null` on every failure mode (network error, non-OK response, bad JSON, an unexpectedly-shaped body) — there's no code path in this feature that can throw into the caller.
    - `locationLabel` (and the in-flight promise ref) are both cleared synchronously the moment `coords` changes (not just when the async response lands) — submitting while a fresh lookup for a *just-changed* location is still in flight sends `null` if the 4s wait also elapses, never the previous location's now-mismatched descriptor. `null` is always a safe thing to submit; a stale-but-present label wouldn't be.
    - Shown to the user before submission in the "Pinned ✓" banner (a lighter sub-line, `.pinned-location`, under the exact lat/lon — "Finding the address…" while resolving, the descriptor once resolved, nothing if resolution finished with nothing), and after submission on the listing's own popup/detail card under the note (`.compact-location`, `ListingDetailModal.tsx`) — only when `location_label` is non-null; absent entirely otherwise, never a placeholder.
    - **Existing listings created before this short-label rewrite** keep whatever `location_label` they already had (`null` for every listing created before a locality-label backfill, if/when one is run) — this is a display-only convenience derived from `latitude`/`longitude`, which remain the sole authoritative location, so a listing missing a label is never treated as broken.
    - **Native mobile is untouched and remains a separate mechanism** — `src/screens/ListingDetailScreen.tsx` already had its own working reverse geocoding (Nominatim/OSM, `src/lib/geocoding.ts`), called live on every Listing Detail view rather than stored. The two platforms now both show a resolved address, via genuinely different code paths, for genuinely different reasons (native's predates this feature and works fine as-is; web's needed to be stored since the Add Listing flow and the popup that later displays it are different sessions/visitors on an anonymous site). Don't try to unify these without being asked.

## Conventions
- Browsing is open with no login on both platforms; mobile requires Google sign-in to post/vote, web is silently anonymous for everyone (see Auth above — these are genuinely different, not a simplification).
- Every listing needs a report/block affordance (required by both app stores for UGC).
- No submission gate on listings — keep friction near zero, quality comes from community upvotes; the content-moderation keyword check is the only automatic gate.
- `npm install` in this repo needs `--ignore-scripts` — a user-level `.npmrc` (`allow-scripts=@anthropic-ai/claude-code`) blocks project-scoped install scripts otherwise. This also breaks `npx expo install`, `npx expo install --fix`, and EAS's auto-install-missing-package step; install the specific version directly via `npm install --ignore-scripts <pkg>@<version>` (check `node_modules/expo/bundledNativeModules.json` for the version this SDK expects), then re-run the command that wanted it.
- After any mobile change, verify with `npx tsc --noEmit` and `npx expo export --platform android` (then `rm -rf dist`) before calling it done — this catches native-module/bundling breakage that a typecheck alone won't. For web, `npx tsc --noEmit` (or `npm run build` in `web/`, which runs `tsc -b && vite build`) — both currently pass clean.
- **A root-level `npm test` now exists** (`node --test "tests/*.test.mjs"` — Node's own built-in test runner, zero dependencies) for pure, dependency-free TypeScript logic shared across platforms — `tests/placeRanking.test.mjs` and `tests/locationProvenance.test.mjs` as of this writing. The convention behind it: extract the pure core of any per-platform-duplicated logic (name/type ranking, location-provenance rules) into a small zero-import module per platform, so the exact same test file can import and exercise all copies at once and they can't silently drift. A file that imports anything Deno-specific (`npm:` specifiers) or anything that reads `import.meta.env`/constructs a real client at module load (e.g. `./supabase`) will break plain-Node resolution the moment it's imported, even for one unrelated export — split the pure part into its own file first, the same way `extractGoogleCoords.ts` was split out of `googleMapsLink.ts`.
- The user's dev phone (Android) can't reach this PC over their normal Wi-Fi/hotspot setup (a known Android hotspot NAT quirk blocks the host phone from reaching its own hotspot clients) — `npx expo start --tunnel` is the reliable way to connect the dev-client to Metro, not a plain LAN `npx expo start`.
- **Local and production never auto-sync, and no tool may ever write to production as a side effect of a local command.** Local is for testing; production changes are always an explicit manual action. Any future production-import capability must be a separate, deliberately-invoked workflow — never a flag bolted onto a local script (see the Excel importer's own guards under `tools/discovery/`). Never treat local data as a mirror of production: the two have already diverged in both directions.
- **Never submit/create/delete/vote/report against the production Supabase project during development/testing without the user's explicit go-ahead on that specific action first** — both mobile's `.env` and web's `.env` point at the same live production project (`nvingzluboafxzxgxxwc`), so any insert/delete/vote/report call from either app during dev writes real rows into the same database real users see. Read-only `select` queries against production are fine without asking each time. For anything that writes, either get explicit approval for that specific action, or exercise it against the local Docker Supabase stack instead (see "Local dev uses a fully local Supabase stack" above).

### The qualification-rule correction — READ THIS PART CAREFULLY, it went through five designs in one day

The rule for whether a Dish + Price entry qualifies was revised repeatedly on 2026-09-04, in a separate follow-up conversation after the rest of this feature was already built. **The final, approved, currently-implemented version is price range alone — nothing else.** Every earlier design listed below was tried, or proposed, and then explicitly superseded; none of them are what's in `dishes.ts` now.

1. **v1 (built, then rejected)**: ported `tools/discovery/matching.mjs`'s `classifyOffering`/`looksLikeCompleteMeal`/`looksLikeSubstantialDish` — required an explicit meal/thali/combo/breakfast keyword or a connector (`+`/"and"/"with") before ANY dish name could qualify. Rejected: it blocked legitimate entries like **"Dosa ₹50"** for lacking a magic word.
2. **v2 (built, then rejected)**: a short exact-match blocklist (`idli`, `vada`, `roti`, `chapati`, `tea`, `coffee`, with a leading quantity word stripped before matching). Rejected: it missed anything not on the list — **"2 boiled eggs"**, **"3 bananas"**, **"2 samosas"** are all obviously single-serving items, but a hand-maintained word list was never going to include them all.
3. **v3 (proposed and planned in detail, never built)**: a per-dish "is this a full meal?" self-declaration checkbox, unchecked by default. Explicitly rejected before implementation — the product call was to add no further qualification UI at all.
4. **v4 (built, then rejected)**: combined a bare-beverage check (`tea`/`coffee`) with a leading-quantity check (any dish opening with a count, e.g. "1 Idli") — rejected UNLESS a multi-item connector (`+`/"and"/"with"/comma) was also present, so "Idli + Vada" still qualified. This correctly handled every one of the originally-given accept/reject examples, but was explicitly rejected anyway: the final product decision was that **no wording or quantity-based rejection of any kind belongs in this rule**, full stop — not even a narrow, two-signal version.
5. **v5 — FINAL, currently implemented**: **price is the only signal.** `MIN_DISH_PRICE = 30`, `MAX_DISH_PRICE = 100`, both inclusive, and nothing else. There is no blocklist, no keyword requirement, no quantity/connector detection, no beverage exclusion, and no `isQualifyingDish`/`isBlockedSingleItem`-style function of any kind in `dishes.ts` — `validateDishDrafts()` checks shape, then price range, then pushes the entry. Bare **"Dosa"**, **"Masala Dosa"**, **"Biryani"**, **"Chicken Rice"**, **"Meals"**, **"Thali"**, **"Breakfast"** all qualify with no keyword required — and so, deliberately, do **"1 Idli ₹30"**, **"2 boiled eggs ₹30"**, **"3 bananas ₹30"**, **"2 samosas ₹30"**, **"Tea ₹30"**, and **"Coffee ₹30"**. Questionable listings are left to the existing report flow and admin moderation, not algorithmic food classification. `tools/discovery/matching.mjs` is completely untouched and unreferenced anywhere in `dishes.ts`, across every version above — confirmed via `git diff` showing zero changes to that file throughout.

**Exact current rule and copy** (both platforms, identical):
- Price: ₹30–₹100 inclusive. `MIN_DISH_PRICE = 30`, `MAX_DISH_PRICE = 100`. Message: **"Price must be between ₹30 and ₹100."** This is the only validation error `validateDishDrafts()` can return for dish content (blank-dish/blank-price/non-numeric-price checks are separate, unrelated to qualification).
- There is no second error message — `SINGLE_ITEM_ERROR` and every function that used to produce it were removed in the final pass. If either name is seen referenced anywhere else in this repo (an older commit message, a stale comment), it's describing a superseded design, not current behavior.

**The Iyer Mess case, explicitly**: its real listing (local and production) still has `price_rupees: 10`, `dishes: null`, `rating: null`, and the same original note — confirmed via a direct read-only query, byte-unchanged, nothing fabricated or backfilled. `tests/dishes.test.mjs` has a dedicated test proving the validator rejects "Vada ₹10" on price alone (₹10 is under the ₹30 floor) and — unlike every earlier design — now legitimately **accepts** a hypothetical "Vada ₹70", since price is the only gate left. This is the accepted trade-off of the final rule, not a regression: a single vada at a real meal price is treated the same as any other dish name.

## Local discovery/verification pipeline (`tools/discovery/` — local-only tooling, NOT part of the deployed app)

A separate pipeline (built 2026-09-01, across phases 1.1–1.12, local-only through phase 1.12) to bootstrap real Beggars Map listings from Google Places. Its research/matching/verification stages (items 1–8 below) remain local-only by design; item 9's Excel importer later grew an explicit, opt-in `--production` mode (2026-09-02) that has since been used once, for 7 human-approved rows — see "Eight rows have been imported" below and item 9's production-mode documentation for the full detail and safety model. **Hard-gated against touching production by accident**: scripts 1–8 below (discovery through `import-approved.mjs`) only ever target the local Docker Supabase stack (via `supabase db query --local`, discovering the container by its `com.supabase.cli.project` label — the exact same pattern `scripts/restore-local-db.mjs` already used) and have no `--linked`/`--project-ref` code path at all. **The one exception is item 9, `import-excel.mjs`**, whose production mode is opt-in (`--production`, plus a separate `--execute` to actually write), preflight-gated to one hard-coded project ref, and detailed in its own section below — see that section, not this sentence, for its safety model. All state lives in `tools/discovery/output/` (gitignored) as timestamped JSON/CSV files; each phase writes a *new* file rather than mutating an earlier one, so the timestamps in the filenames are the history.

**Pipeline stages, in the order data flows through them:**
1. **`discover.mjs`** — Google Places API (New) Text Search across `config.mjs`'s area × category grid (35 Bengaluru areas spanning all 9 geographic zones — North/South/East/West/Central/Northeast/Northwest/Southeast/Southwest — and 28 categories prioritizing complete-meal terms: darshini/tiffin/mess/thali/bhojanalaya/military hotel/biryani/regional-meals-Punjabi-Kerala-Andhra-Karnataka/etc., with generic "restaurant" searches deliberately pushed to the end of the list and excluded from a curated run). `places-client.mjs` requests only `id/displayName/formattedAddress/location/priceLevel/types/primaryType/businessStatus/websiteUri/nationalPhoneNumber/googleMapsUri` — never photos/reviews (policy: never copy Google's restricted content into Beggars Map). `dedupe.mjs` merges hits by `place_id`, preserving full provenance per hit (`area`, `query`, and a per-hit `discovered_at` timestamp) rather than collapsing to one entry. **Two real datasets exist**: an early 127-candidate one (only 4 areas — Koramangala/Indiranagar/Jayanagar/Malleswaram, all South/Central — superseded, kept only for history) and the canonical **3,604-candidate, genuinely city-wide one** (`candidates-2026-09-01T11-50-51-056Z.json`, 770 API calls, 9-zone coverage confirmed via `analyze-dataset.mjs`) — always use the latter unless explicitly told otherwise.
   - **Google Places key**: a dedicated server-side `GOOGLE_PLACES_API_KEY` lives in `tools/discovery/.env` (gitignored, `.env.example` alongside it) — deliberately *not* the browser-restricted `VITE_GOOGLE_MAPS_API_KEY` (that one is HTTP-referrer-restricted and fails outright from a Node script; confirmed live). The discovery key itself carries an **IP allowlist restriction** — confirmed to fail with `API_KEY_IP_ADDRESS_BLOCKED` when Node's fetch happened to resolve the dev machine's IPv6 address instead of its allowlisted IPv4 one; fixed by running with `node --dns-result-order=ipv4first`, never by touching the key's own restrictions (same standing rule as the Maps JS key: don't modify a key's restrictions without the user's explicit go-ahead).
2. **`matching.mjs`** — shared logic every downstream stage imports: `matchConfidence()` (branch-collision guard — a name match alone is capped at `medium`; only an address/locality token-overlap against the candidate's own `formatted_address` earns `high` — exists because Bengaluru darshini/udupi naming repeats constantly, e.g. several unrelated "New Udupi Grand" branches citywide); `classifyOffering()` (the core product-policy gate — **Beggars Map lists complete affordable meals, not any-cheap-item restaurants**: a ₹10 vada or one roti never qualifies alone, even though it's technically "an item ≤₹100" — requires an explicit `offering_type` ∈ `BREAKFAST/MEAL/THALI/COMBO/SUBSTANTIAL_SINGLE_DISH/SINGLE_ITEM` *and* the evidence text itself independently reading as multi-component, via a keyword like "meal"/"thali"/"combo"/"tiffin" or items visibly joined by `+`/comma/"and"/"with"; `SUBSTANTIAL_SINGLE_DISH` is the one exception, for a dish like a full biryani that's inherently a complete meal alone, gated by its own keyword list so a bare "half chicken" still can't sneak through); `duplicateRisk()`/`haversineKm()` (import-time guard against creating a duplicate of an already-existing local listing, by proximity + name overlap, deliberately tuned to over-flag rather than under-flag).
3. **`price-verify.mjs`** — the original research prototype (Phase 1.5): a small hand-picked set of candidates, researched by the agent via `WebSearch` (never scraping — Zomato was found to be technically unreachable from this environment/connection blocked; Swiggy's own Terms & Conditions explicitly forbid "page-scrape"/"robot"/"spider" access; neither is ever fetched directly, only search-engine snippets and a restaurant's own site when one exists). Superseded by `research-batch.mjs` for full-dataset work, but its output (and the 11 candidates it researched) is still read by later stages.
4. **`verify-queue.mjs`** — an interactive CLI for a **real human** to review candidates one at a time and explicitly approve/reject. This is the *only* place `HUMAN_VERIFIED_LE_100` can legitimately originate — **research findings (from `price-verify.mjs` or `research-batch.mjs`) must never be presented or coded as human-verified, only as `QUALIFIES_PENDING_HUMAN_REVIEW`**; this is enforced in code, not just convention (both `research-batch.mjs`'s and `reverify-batch.mjs`'s result validators hard-reject any attempt to commit `HUMAN_VERIFIED_LE_100`, and the human-review workbook ships with every decision cell blank). Approval requires typing an `offering_type` plus a description that itself passes `classifyOffering()` — a reviewer mistagging a single item as `MEAL` still gets refused. Uses a hand-rolled pull-based line reader (`makeLineReader`) instead of `readline/promises`' `question()`, because that hung after the first call against piped/non-TTY stdin in this environment (reproduced in isolation) — don't revert to plain `readline/promises` here.
5. **`build-queue.mjs` / `build-city-queue.mjs`** — curated-selection scripts that score+rank candidates (INEXPENSIVE signal, meal-keyword strength, discovery-hit-count, prior-evidence bonus) and select a diverse subset with **zone-balanced** (an equal-ish quota across all 9 zones, deliberately *not* proportional to raw discovery counts — proportional would just recreate the South/Southeast dominance already present in the raw data) and **brand-capped** (`brandKey()` strips common words like "new"/"sri"/"grand" to detect same-brand clusters and avoid one chain's branches flooding the list) selection. `build-city-queue.mjs` (Phase 1.10, ~200 candidates from the full 3,604) is current; `build-queue.mjs` (Phase 1.8, ~30 candidates from the old 127) is superseded.
6. **`research-batch.mjs`** — resumable, full-dataset research driver (Phase 1.11) for working through all 3,604 candidates in manageable batches, since WebSearch-based research is inherently agent/human-paced, not something a script can run end-to-end unattended. `--generate-worklist --batch-size=N` picks the next N unresearched candidates (score-prioritized, area-capped) and marks them `in_progress` in `research-state.json`; the agent then actually researches them via `WebSearch`; `--commit-results=path.json --batch=N` validates each result (via `classifyOffering`) and merges it into the growing master `full-verification-results.json`/`.csv`, marking it `completed`. Interrupting mid-batch loses nothing — `in_progress` entries just regenerate into a fresh worklist next time. **As of the last session, batches 1–5 are committed: 250 of 3,604 researched, 3,304 pending** (`node tools/discovery/research-batch.mjs --status` reports live progress). Status split across those 250: 139 `PRICE_UNKNOWN`, 38 `SOURCE_UNAVAILABLE`, 25 `MATCH_UNCERTAIN`, 20 `QUALIFIES_PENDING_HUMAN_REVIEW`, 18 `EVIDENCE_FOUND`, 10 `PRICE_ABOVE_100` — **none human-verified**. Two operational notes: (a) `research-state.json` currently carries **50 entries stuck `in_progress`** from a batch-6 worklist generated moments before the run was stopped — those 50 were never researched and are not part of the 250; they are harmless (a fresh `--generate-worklist` re-picks them) but will look like a 50-candidate gap in the arithmetic until cleared. (b) Batches 2–5 were driven by a `/loop` in dynamic self-pacing mode (one batch per wakeup, ~20 min apart), which works but is *not* how to run this unattended long-term — see the Phase 1.12 note below on why the output needed re-verifying anyway.
7. **`reverify-batch.mjs` + `build-reverification-workbook.py`** — Phase 1.12, the **re-verification layer over the existing 250**, built because the Phase 1.11 pass proved **too shallow to trust as final**. The trigger was a concrete counter-example: "Madura Darshini Vegetarian" had been recorded `SOURCE_UNAVAILABLE`, yet an ordinary public Google result exposes a Zomato page with menu-highlight prices, and its address panel (32/21, Bellary Rd, Ganganagar) matches the candidate exactly. `reverify-batch.mjs` mirrors `research-batch.mjs`'s resumable shape (`--generate-worklist` / `--commit-results=path --batch=N` / `--status`) but reads its universe from `full-verification-results.json` **read-only**, keeps its own `reverification-state.json`, writes `reverification-250.json`/`.csv`, and **refuses any `place_id` that isn't one of the 250** so a re-verification pass can never smuggle in new candidates. It carries the same hard rejection of `HUMAN_VERIFIED_LE_100` and the same `classifyOffering()` gate, plus validation of the two new structures below. `build-reverification-workbook.py` (Python 3.12 + openpyxl 3.1.5, both already available on this machine) renders `reverification-250-human-review.xlsx` — Instructions / Review / Summary sheets, every **HUMAN DECISION cell blank** with an APPROVE/REJECT/UNCERTAIN/NEEDS MORE RESEARCH dropdown, frozen header, filters, ₹ formatting, clickable URLs, and **old status shown beside new status with changed rows highlighted** (the whole point is catching where the first pass was wrong in either direction).
   - **Two separate kinds of food data, deliberately not conflated.** `cheap_items_under_100[]` collects individually cheap items (each `item_name`/`price_rupees`/`source`/`source_url`/`evidence_description`) — useful as listing-note colour, but these **never qualify a restaurant**, and a meal is never synthesised by summing them. Only a genuinely complete meal/breakfast/thali/combo/substantial single dish produces `QUALIFIES_PENDING_HUMAN_REVIEW`. `image_urls[]` became structured too (`url`/`image_type` ∈ `EXTERIOR/SIGNBOARD/MENU/FOOD/MEAL/OTHER`/`source`/`source_page`/`provenance`), and stays empty rather than holding a guessed URL.
   - **`SOURCE_UNAVAILABLE` now means "reasonable public-source research found nothing", not "the first query missed".** Batch 1 of the re-verification cut that bucket from 8 to 2 out of 50 purely by trying name+area, name+address, menu/meals/price-targeted queries before giving up — most "unavailable" entries were simply under-searched.
   - **Batch 1 of 5 is done (50 of 250 re-verified, 24 status changes).** Qualifying rose 4→8 for those 50; newly surfaced meals the first pass missed include Sri Rajarajeshwari Iyer Mess (₹90 meal, phone-matched), Upahara Darshini 9th Block (₹49 breakfast combo), New K V Canteen (₹60 meals plate) and JCL Canteen (₹65 ghee pongal). It also corrected in the *other* direction: Iyer Mess was downgraded to `EVIDENCE_FOUND` because published prices conflict across the cap (₹115 list / ₹49 platform offer / ₹70 previously), and four `PRICE_ABOVE_100` calls that rested only on cost-for-two aggregates became `PRICE_UNKNOWN`. **Batches 2–5 are not started and need explicit go-ahead.**
   - **Conventions this pass settled, worth keeping:** an aggregate "cost for two" is *never* item-level evidence — it can support `EVIDENCE_FOUND` or `PRICE_UNKNOWN` but never `PRICE_ABOVE_100` or a qualifying price. Conflicting prices that straddle ₹100 get `EVIDENCE_FOUND` with the conflict flagged, never a guess. Evidence the *user* supplies (e.g. a screenshot of a public result) is valid but recorded with explicit **USER-SUPPLIED** provenance, distinct from anything the pass fetched itself. Government **Indira Canteen** branches recur constantly across the dataset (₹5 breakfast / ₹10 lunch-dinner: rice, sambar, curry, curd rice, program-wide fixed pricing) — they qualify mechanically but are still flagged for human review as institutional canteens rather than private restaurants. And branch-collision keeps biting in new ways: "Kovai Mess, Gandhipuram" is in **Coimbatore** (Kovai = Coimbatore) while the candidate's "Gandhipuram" is a Whitefield locality — a same-name-locality trap, not just a same-name-restaurant one.
8. **`import-approved.mjs`** — one of only two scripts here that write to a database, and only ever the local one. Reads a human-approved candidate (from `verify-queue.mjs`'s `verified-candidates.json`), re-validates everything from scratch (never trusts the upstream file), checks for duplicates against both its own prior-import manifests and a live read of the existing local `listings` table, and only then inserts — always `is_hidden: true` by default. `--dry-run` (the default) vs `--yes` to actually write.

9. **`import-excel.mjs` (+ `xlsx-to-json.py`)** — the **Excel bulk-import workflow**, added 2026-09-02. Distinct from `import-approved.mjs`: that one reads `verify-queue.mjs`'s JSON and handles no photos at all; this one's input is the spreadsheet a human marks up by hand (`tools/discovery/output/candidates-*-workonprogress.xlsx`), and it uploads photos. `xlsx-to-json.py` is a deliberately dumb converter with no business logic (openpyxl is already a dependency here, and Node has no xlsx reader — adding one would mean a new npm dependency, awkward in this repo); every qualifying decision lives in the `.mjs` so there is one place to audit.
   - **`Menu List Under 100` = exactly `Yes` (trimmed) is the sole qualification gate.** `No`, blank, or anything else is skipped. No other signal — Google price level, individually cheap items, discovery score, `classifyOffering()` — can qualify a row in its place; that column is the human decision the script defers to. Conversely a `Yes` row is never second-guessed by the offering-type model.
   - **Price = the minimum integer in `Menu Details/Notes`**, with URLs stripped first (so a domain like `foo123.com` can't be read as a price) and with **quantity markers excluded**: a number immediately followed by `nos`/`no`/`pcs`/`pc`/`piece`/`pieces` (any case, with or without a space) is a count, not a price. This came from a real row — `"Biryani rice 90, parotha(2nos) 60, rahi ball(2nos) 60"` — which extracted **₹2** and would have imported as the cheapest listing on the map; it now correctly yields ₹60. The trailing `\b` in that lookahead is load-bearing: without it `no` matches the start of `north`, and `"50 north indian thali"` loses its ₹50. The pattern is written as a single regex literal on purpose — assembling it from a template string collapses `\d` to a plain `d` and silently breaks `[\d.]`. If every number in a note carries a quantity marker, the row is skipped as "no numeric price found" rather than importing a count as a price.
   - **`Menu Details/Notes` → `listings.note`, byte-for-byte unchanged** (verified by md5 against the source cells). This is why `sqlString()` emits any non-printable-ASCII character as a `chr(N)` concatenation instead of placing it in the SQL argument literally: `supabase db query --local` receives its SQL as one shell argument, and a raw newline in that argument arrives at Postgres as the two literal characters `\` and `n`. Don't revert that to plain quote-doubling.
   - **Excel `latitude`/`longitude` → the listing's coordinates**, used as-is.
   - **`location_label` is resolved via the same OLA reverse-geocoding logic the web app uses** (`/places/v1/reverse-geocode`, "Street, Area" preferred, area or city as fallbacks, `null` rather than a fabrication) — resolved once up front so a dry run reports the exact label the real import would store, and reused at insert time rather than looked up twice. The key is read from `OLA_MAPS_API_KEY`, else the existing app `.env` files; with no key, labels are simply `null`.
   - **Photos are matched STRICTLY by the row's hidden `place_id` → `tools/discovery/photos/<place_id>/`, and by nothing else.** Never by name, address, phone, or any fuzzy/similarity matching — a wrong photo on a real restaurant is worse than no photo. Every file in that folder is uploaded to `listing-photos` at `<owner>/<place_id>/<filename>` (the owner prefix is what the bucket's RLS policies key off; the `place_id` segment keeps each photo traceable to the row that claimed it). No folder, or an empty one, imports the restaurant with no photos rather than skipping it.
   - **Multiple photos land in `listing_photos`** (position 0..n-1), with photo 1 *also* written to `listings.photo_url` — the same convention `AddListingModal.tsx` already uses, so single-photo consumers are unaffected. The listing row and all its photo rows go in as **one statement** (a data-modifying CTE, not `begin`/`commit` — the CLI runs its argument as a prepared statement and rejects multiple commands), so a crash can never leave a listing with half its photos.
   - **Every import defaults to `is_hidden = true`.** Nothing this script creates becomes publicly visible on its own; unhiding is a separate, explicit, per-listing decision.
   - **Resumable and duplicate-safe on two independent layers**, because a state file alone can lie (deleted, stale, or written after a crash): `output/excel-import-state.json` records each imported `place_id`, its `listing_id` and its uploaded photos; and before *any* insert the live target database is re-read and checked with `matching.mjs`'s `duplicateRisk()` plus an exact name+coordinate match. A hit skips the row even if the state file has never heard of it, and a state entry whose listing has since been deleted is treated as stale rather than as a block. Photo uploads are idempotent (an object already in storage is left alone). Re-running after a completed import reports "Nothing to import."
   - **Known gap:** it skips already-imported rows by `place_id` and does **not** re-sync later Excel edits — change a price or note for an already-imported restaurant and the run will report it as "already imported" and leave the stored value alone.
   - **Local by default, production only on explicit opt-in.** The importer has exactly two modes, and the safe one is what you get with no flags.
     - **Local mode (default).** `--dry-run` is implied; `--yes` writes. `--status` lists what's been imported; `--backfill-location-labels` fills `location_label` on rows this importer created that have none (only null ones, only its own rows — local only). Every SQL statement goes through `supabase db query --local`, and the storage API URL comes from `supabase status` and is asserted to be loopback before anything is written. Passing `--linked` or `--project-ref` exits(1) with `REFUSING TO RUN`.
     - **Production mode (`--production`, added 2026-09-02).** Reuses the same code — the same qualifying gate, the same price extraction, the same photo matching, the same duplicate checks — with only the I/O swapped behind two small adapters (`--local` vs `--linked` for SQL; the loopback HTTP uploader vs `supabase storage cp` for photos). There is deliberately **no second importer**.
   - **Production-import safety rules — all of these are enforced in code, not convention:**
     - **The target is hard-coded**, not read from a flag or any `.env`: `PRODUCTION_PROJECT_REF = 'nvingzluboafxzxgxxwc'`. `--linked`/`--project-ref` are refused in *both* modes, so the destination can never be steered from the command line.
     - **Preflight must pass before a single Excel row is read.** The *linked* project must be exactly that ref (a machine linked to RentalIntel — or to nothing — aborts by name), `listings` and `listing_photos` must both exist, the `listing-photos` bucket must exist, and the owner profile (`00000000-…-0001`, "Beggars Map Team" in production) must exist so no insert can fail halfway on a FK. Each check prints as it passes.
     - **A dry run is mandatory and is what `--production` alone does** — zero writes, and it prints the full plan: rows selected by `Menu List Under 100 = Yes`, rows already imported per the state file, rows already present or duplicate-risky in the *live production* database, the rows that will be inserted with their extracted price/notes/coordinates/`location_label`/photo folder/photo count, and a **PLANNED WRITES** block totalling listings, `listing_photos` rows, photo uploads, database statements, storage operations, and the grand total.
     - **Writing requires BOTH `--production` and `--execute`.** Either flag alone never writes. `--yes` is refused in production mode (it is the local write flag), so muscle memory can't cause an import.
     - **No production service-role key is ever read, stored, or passed around.** SQL goes through the CLI's own authenticated connection, and photos through `supabase storage cp`, which uses the developer's Supabase login. (`storage ls`/`cp` need `--experimental` in this CLI version; note `ls` prints JSON by *default* and plain text with `-o json`, which is the opposite of what you'd expect.)
     - **Duplicate protection is per-environment and checks both sources**: the state file keeps production entries in their own namespace (`environments.production.entries`) so a local test import never makes production look done, and before every insert the *production* database is re-read and checked with `duplicateRisk()` plus an exact name+coordinate match.
     - **Imports are `is_hidden = true` and are never unhidden by this script.** Making something visible in production is a separate, deliberate human action.
     - **Nothing is ever UPDATEd or DELETEd.** The only statement it issues is an INSERT (listing + its photo rows as one atomic data-modifying CTE); photo uploads are idempotent, so an interrupted run resumes without re-uploading.
   - **Exact production command sequence** (never skip step 2, and read its output before step 3):
     ```
     npx supabase link --project-ref nvingzluboafxzxgxxwc     # 1. only if not already linked
     node tools/discovery/import-excel.mjs --production        # 2. MANDATORY dry run, zero writes
     node tools/discovery/import-excel.mjs --production --execute   # 3. the actual import
     node tools/discovery/import-excel.mjs --production --status    # 4. what landed
     ```

**Schema gap, reported rather than papered over**: `listings` has no column for `place_id`, evidence source URL, match confidence, qualifying item, offering type, or verification timestamp — none was invented (per explicit instruction: if the schema can't represent provenance, report the gap, don't modify the schema).
