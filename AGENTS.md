# Expo SDK is pinned to 54 — do not upgrade without asking

The project was scaffolded on SDK 57 but was rolled back to **SDK 54** because the Expo Go app on the Play/App Store lags behind the latest SDK (Apple review delays especially) and can't open newer-SDK projects. Bump back up only once Expo Go in the stores has caught up, or once you're fully off Expo Go and building exclusively via EAS dev-client. Read the versioned docs at https://docs.expo.dev/versions/v54.0.0/ before writing code that depends on SDK-specific APIs.

# Beggars Map

Crowdsourced map/directory of cheap eats in Bengaluru (India take on Korea's viral "Geoji Map" / 거지맵). **₹100 price cap** — listings must be ₹100 or under, sort cheapest-first, community upvotes surface quality. (Decision changed 2026-08-25: originally "no cap," the user revised this to match Geoji Map's own hard cap — see full product plan and prior locked decisions in Claude's memory `project-beggars-map`, but this price-cap change supersedes what's written there.)

**Two independent apps, one Supabase backend:** a React Native mobile app (repo root, `src/`) and a Vite/React web app (`web/`). They diverge more than a typical "shared backend, thin client differences" setup — see Auth below in particular, where mobile requires sign-in and web is anonymous-only by design.

**Web app status:** built and live at `beggarsmap.com` (Vite + React, deployed on Vercel — see memory `project_launch_status` for domain/hosting detail), solving the original app-only zero-friction-access gap vs. the Korean original. Mobile is dev-client only so far — no store listing yet (see Launch status below).

**Price cap implementation status:** enforced end-to-end — DB constraint via `0004_price_cap.sql` (`price_rupees > 0 and price_rupees <= 100`), plus client-side validation in both `AddListingScreen.tsx` (mobile) and `AddListingModal.tsx` (web). The `0003_seed_demo_listings.sql` seed data was also brought under the cap (one demo listing was ₹180) since it runs before `0004` and would otherwise break that migration on a fresh `supabase db reset`.

## Stack
- Expo (React Native) + TypeScript, SDK 54, `blank-typescript` template, mobile only
- Web: Vite + React + TypeScript (`web/`), no router — single `App.tsx` with modal-driven navigation (Add Listing, Listing Detail, Legal all render as modals over the map, not separate routes)
- Navigation (mobile, `src/navigation/`) — root stack (`Tabs`, `ListingDetail`, `AddListing`, `PickLocation`, `SignIn`, `Legal`) wrapping a bottom tab navigator (`Map`, `Contribute`, `Leaderboard`, `Profile`). The `Contribute` tab never renders its own screen — its `tabPress` is intercepted and redirected to `AddListing`/`SignIn` on the root stack, so it needs `Map` to stay in the tab bar as the way back (don't remove `Map` from the tab bar without restoring another path back to it).
- Map (native/mobile only — see below for web, which uses Google Maps instead): OLA Maps (India-tuned, dedicated key in `EXPO_PUBLIC_OLA_MAPS_API_KEY`, not shared with RentalIntel's key — see budget note below). Layers:
  - **Interactive map** (`src/components/ListingsMap.tsx`, used on the Map screen; `src/screens/PickLocationScreen.tsx`, used for manual pin placement in Add Listing): `@maplibre/maplibre-react-native` pointed at OLA's vector tile style JSON (`vectorStyleUrl()` in `src/lib/olaMaps.ts`). **Native module — will not run in Expo Go.** Requires an EAS dev-client build, already set up (`eas.json`, EAS project linked under `nikhil_sinha/BeggarsMap`) — rebuild via `npx eas-cli build --profile development --platform android` only when a *native* dependency changes; pure JS/TS changes just need a Metro reload, no rebuild.
  - OLA's style JSON references tile/sprite/glyph URLs that don't carry the API key themselves — `src/lib/olaMaps.ts` registers a `TransformRequestManager.addUrlSearchParam` transform at module load to append `api_key` to every request to `api.olamaps.io`. If you see 401s on sources/sprites/glyphs, this is the first thing to check.
  - Markers use `anchor="bottom"` (pin tip points at the coordinate) — the default `"center"` anchor caused pins to visually overflow their container.
  - **Static map fallback** (`staticMapUrl()` in `src/lib/olaMaps.ts`): plain `<Image>` hitting OLA's static-map REST endpoint, no native module needed — works in Expo Go. Superseded by the interactive map on the Map screen but kept as a lightweight-preview helper.
  - **Places search** (`searchPlaces()` in `src/lib/olaMaps.ts`): OLA's autocomplete endpoint, used from both `MapScreen.tsx` (landmark search that flies the camera) and `PickLocationScreen.tsx` — each screen independently debounces its own call to this function and drives its own camera `flyTo`; this is duplicated per-screen logic (not a shared hook), a known tech-debt item, not a functional bug.
  - No in-app turn-by-turn navigation. Listing Detail's "Directions" button hands off to the device's Google Maps / Apple Maps app instead (same pattern as Zomato/Swiggy).
  - **Scaling risk**: if this goes viral, OLA's free tier (500K loads/month) is the first thing to break — well before Supabase's free-tier limits. Upgrading is just a paid-plan flip, no code change, but budget for it if growth is real.
- Map (web only, `web/`): **hybrid** — Google Maps JS API renders the map, OLA Places handles search. Rendering migrated off MapLibre 2026-08-28: `web/src/lib/googleMaps.ts` loads the JS API via Google's official inline dynamic-import bootstrap snippet (not an npm loader package — `google.maps.importLibrary('maps'|'marker')`), keyed by `VITE_GOOGLE_MAPS_API_KEY`. `web/src/components/MapView.tsx` renders the map and `AdvancedMarkerElement` pins (needs `VITE_GOOGLE_MAPS_MAP_ID` — a Map ID created in Cloud Console, separate from the API key). **Place search reverted to OLA Places 2026-08-28** (same day): Google Places API (New) was tried first but its per-request billing (Autocomplete + Place Details Essentials SKUs, ~$0.85–1.50/1000 in India after a 70k/month free quota per SKU) looked expensive for a search box that also does local listing-name filtering, so `web/src/lib/olaPlaces.ts` (search-only — no map-tile responsibilities, unlike the old pre-migration `olaMaps.ts` this was revived from and which is now deleted) does `searchPlaces()` against `api.olamaps.io/places/v1/autocomplete`, free tier, keyed by `VITE_OLA_MAPS_API_KEY` (yes, both a Google key and an OLA key are configured for web — normal for this hybrid, not a leftover). `App.tsx`'s home search box only fires the external OLA call when the query has **zero local listing matches** (`filtered.length === 0`) — normal typing that matches an existing listing never reaches OLA at all. **Reverse geocoding was removed, not migrated**: the old `web/src/lib/geocoding.ts` (Nominatim/OSM address lookup for the listing popup) is deleted and nothing replaced it — the web listing popup no longer shows a street address, only the listing's own name/note. Forward geocoding was never needed on web: Google Maps share-link parsing (`googleMapsLink.ts`) extracts lat/lng from the URL itself, no API call.
  - **The selected-listing popup is no longer a Google `InfoWindow`** (changed this pass). `InfoWindow` content renders inside Google's own nested map panes, which bundle the base map tiles and every overlay under one shared stacking rank from any *sibling* element's point of view (`.list-panel-outer`, the restaurant list) — empirically, no z-index could put an `InfoWindow` above the side panel without the base map tiles also winning, breaking the "panel floats over the map" look. `MapView.tsx` now positions its own plain `.map-popup-anchor`/`.map-popup-card` divs by directly measuring the selected pin's own DOM element (`selectedMarkerElRef`, via `getBoundingClientRect()` on a `requestAnimationFrame` loop while a popup is open) rather than Google's Projection API, which proved unreliable for this (empirically returned near-`(0,0)` for real coordinates in testing, independent of raster/vector rendering mode). The popup card sits at `z-index: 10`, comfortably above `.list-panel-outer` (`z-index: 4`) as true DOM siblings. A minimum-clearance clamp (`Math.max(pinTop, 190)` in the position-measuring effect) keeps the card from opening underneath the search bar when the pin is near the top of a short frame (routine on mobile landscape) — since dropping `InfoWindow` also dropped its automatic auto-pan-into-view behavior, this is a deliberate, accepted trade-off, not a bug.
- Auth — **deliberately different per platform, do not unify without being explicitly asked:**
  - **Mobile**: Supabase Auth, **Google OAuth only** (`src/lib/auth.tsx`). Phone OTP was deliberately dropped: no SMS provider configured and the user doesn't want phone billing. Browsing is open with no login; sign-in is required only to post a listing or vote.
    - Supabase client (`src/lib/supabase.ts`) must set `flowType: 'pkce'` explicitly — the supabase-js default is `'implicit'`, which breaks the `exchangeCodeForSession` call in `auth.tsx`.
    - On Android, `WebBrowser.openAuthSessionAsync` sometimes resolves `dismiss` instead of `success` when the OAuth redirect hits the app's custom scheme (the OS hands the deep link straight to the app, closing the browser as a side effect). `signInWithGoogle` in `auth.tsx` races the `WebBrowser` promise against a `Linking` `'url'` event listener to catch this case — don't simplify that back down to just awaiting `openAuthSessionAsync`.
    - Google Cloud OAuth client must be **"Web application"** type (not Android/iOS — those use a different, incompatible verification method), with `https://nvingzluboafxzxgxxwc.supabase.co/auth/v1/callback` as the authorized redirect URI, and Supabase's own **Redirect URLs** allowlist (Authentication → URL Configuration) must include `beggarsmap://*`.
  - **Web has no sign-in UI at all.** Every visitor silently gets a Supabase **anonymous** session on load (`ensureAnonymousSession()` in `web/src/lib/supabase.ts`, called before any write), plus a matching `profiles` row (`display_name: 'Anonymous contributor'`) since `listings`/`reviews`/`votes.created_by` all FK to `profiles(id)`. This lets any web visitor contribute/vote/report with zero friction. Requires **"Anonymous sign-ins" enabled** in the target Supabase project's Auth settings (dashboard toggle only, no CLI/API way to check or flip it remotely) — as of the last verified check this had been **off** on the production project; confirm it's on before assuming web writes work live. This was a deliberate, explicit decision — web auth was raised once as a possible future addition and the user deferred it; **do not implement web sign-in, or revert web's "anonymous, permanently" legal copy, without the user explicitly raising it again.**
- Backend: Supabase (free tier) — Postgres schema in `supabase/migrations/`, applied in order:
  - `0001_init.sql` — `profiles`, `listings`, `reviews`, `votes`, `reports`, `leaderboard` view, base RLS policies (public read, owner-only write)
  - `0002_storage.sql` — `listing-photos` storage bucket + policies (public read, owner-scoped by `${userId}/...` path prefix)
  - `0003_seed_demo_listings.sql` — 5 real Bengaluru demo listings under a synthetic seed user, for look-and-feel testing. **Still the only content in production** — no real user has submitted a listing yet as of the last check; safe to delete once real listings exist.
  - `0004_price_cap.sql` — the ₹100 hard cap constraint (see above)
  - `0005_star_ratings.sql` — replaced `reviews.worth_it` (boolean) with 4 category star columns (`food_quality`/`hygiene`/`availability`/`maintenance`) and a `listing_ratings` aggregate view. **This entire review/rating system is now dead** — see "Reviews" below.
  - `0006_lock_is_hidden.sql` — a `BEFORE UPDATE` trigger that silently reverts any change to `listings.is_hidden` unless the caller is `service_role`, so an owner can't self-undo a moderator hiding their listing. There is **no in-app moderation dashboard** — hiding/unhiding a listing today means an admin acting with the service-role key directly (e.g. via the Supabase dashboard), not any UI in either app.
  - `0007_delete_policies_and_report_dedupe.sql` — owners can now DELETE their own `listings`/`reviews` outright (not just hide); `profiles`/`votes`/`reports` intentionally have no owner-DELETE (rationale in the migration's own comment: votes already had it from `0001`, profiles die via account deletion, reports have no "undo" concept). Also adds a unique constraint (`listing_id`, `reported_by`, `reason`) so a user can't file the same report reason against the same listing twice — a different reason, or a report on a different listing, still goes through.
  - `0008_grants.sql` — explicit `GRANT` for `anon`/`authenticated` on the core tables. Fixes a **local-Docker-stack-only** bug (fresh `supabase start` doesn't grant table privileges by default the way the hosted project's provisioning does) — confirmed a no-op on the already-correct production grants, kept for consistency across environments.
  - `0009_listing_photos.sql` *(new this pass)* — additive `listing_photos` table for up to 4 photos per listing (web only, see "Multi-photo upload" below). `listings.photo_url` still holds photo #1 unchanged, so every single-photo consumer (mobile entirely, and web's list card) keeps working with no changes of its own.
  - Client reads `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` (mobile, `.env`) or `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (web, `web/.env`) — both gitignored, see each app's `.env.example`. RLS is on everywhere: public read (except hidden listings), writes require `auth.uid()` to match the row owner.
  - **Deployment status — confirmed 2026-08-29 via direct read-only checks against production (anon-key REST queries + `supabase migration list`/`db push --dry-run`/`functions list`, all read-only, nothing was pushed):**
    - `0001`–`0005` are live — confirmed directly (not just inferred): `listings`/`reviews`/`votes`/`reports` all reachable via the anon key, `listings.is_hidden` present, the ₹100 cap holds, and the 5 seed listings from `0003` are the site's only content.
    - **`0009_listing_photos.sql` is confirmed NOT applied** — `GET .../rest/v1/listing_photos` returns `404` in production. Web's `AddListingModal.tsx` has been deployed (this table's consumer) since `e86cd13`, so **any web visitor who adds a 2nd–4th photo today gets a failed insert** — this is an active bug, not a theoretical gap. Top launch blocker.
    - **Zero Edge Functions are deployed** (`supabase functions list` → `[]`) — `delete-account` is confirmed not live. Mobile's "Delete my account" button will fail for any real user who taps it.
    - `0006`–`0008` (moderation lock, delete policies + report dedupe, grants) could not be directly confirmed via anon-key reads alone (they're a trigger/policies/grants, not a new table or column) — treat as **unverified, not confirmed-applied**, until checked from the dashboard or via a live-data test.
    - **A plain `supabase db push` will NOT cleanly deploy just `0009`.** The CLI's own migration-tracking table doesn't know about *any* applied migration (`migration list`/`db push --dry-run` both list `0001`–`0009` as pending, including the ones proven live above) — the production schema was evidently set up without the CLI ever recording versions, so `db push` would try to re-run `0001` first and fail on `relation already exists`. Before pushing, either (a) run `supabase migration repair --status applied 0001 0002 0003 0004 0005` (and `0006`–`0008` too, once those are separately confirmed live) so only `0009` is actually pending, or (b) skip the CLI entirely and run `0009_listing_photos.sql`'s SQL directly via the Supabase dashboard's SQL editor, matching how the rest of the schema apparently got there. Don't run a bare `db push` and assume it's safe.
    - To deploy the Edge Function once ready: `npx supabase functions deploy delete-account --project-ref nvingzluboafxzxgxxwc` (this one has no tracking-desync issue — functions aren't in the migration system).
  - The Supabase CLI is linked to this project only (`nvingzluboafxzxgxxwc` / "Beggars-map") — do not link or run migrations against other Supabase projects in this account (e.g. RentalIntel) from this repo. The link is session-local (`supabase/.temp/`, gitignored) — re-run the link command above if a fresh session needs it.
  - **Local dev uses a fully local Supabase stack, not the production project.** The account is capped at 2 free hosted projects (already used by `Beggars-map` + `RentalIntel`), so local dev runs entirely in Docker instead via `npx supabase start` (requires Docker Desktop running first). This applies all `supabase/migrations/*.sql` to a throwaway local Postgres + Auth + Storage stack — nothing touches the live site's data. `supabase/config.toml` is checked in with `enable_anonymous_sign_ins = true` (the hosted project needs this same toggle set manually — see Auth above). `web/.env.local` (gitignored) points the web app at `http://127.0.0.1:54321` with the local stack's demo anon key instead of the real one — Vite prefers `.env.local` over `.env` automatically. Studio UI for the local stack is at `http://127.0.0.1:54323`. Run `npx supabase stop` when done to free the Docker containers; `npx supabase db reset` re-applies all migrations from scratch if the local data gets messy.
- **Account deletion** (`supabase/functions/delete-account/index.ts`, Deno Edge Function): verifies the caller's own JWT, then uses a service-role client (created only inside the function, never shipped to a client bundle) to `admin.deleteUser` the caller — never any other user. `profiles`/`listings`/`reviews`/`votes` all cascade off `auth.users(id) on delete cascade`, so content goes with the account automatically; the function then does a best-effort cleanup of the user's `listing-photos/{userId}/...` storage objects (a failure there doesn't unwind the account deletion — storage-cost concern, not correctness). **Mobile-only**: wired into `ProfileScreen.tsx` ("Delete my account" behind a confirm dialog). **Web has no equivalent UI at all** — see "Known limitations" below.

## Core UI/UX and major flows
1. **Map** — a large full-screen interactive map (pins, live location) with the cheapest-first list docked below/beside it. City selector, search bar, and an Add button float directly on the map itself as separate pills (not one opaque toolbar), so the map stays visible around/behind them. The Add button's label reads **"+ Add"** (changed from "+ Contribute" this pass — JSX text only, the CSS class stays `contribute-button` so the diff stayed contained). The search bar does double duty: it filters the loaded listings by name locally (no debounce), and separately debounces a call to OLA's places search so searching a landmark (not necessarily a listed spot) flies the map there via an imperative `Camera`/`MapView` ref — see `flyToCenter` prop on `ListingsMap.tsx` (mobile) / `MapView.tsx` (web). Web's search bar is substantially larger/more prominent than before this pass (bigger padding/font on `.search-bar` and its children — scaled down slightly on phone-class widths so it doesn't eat the tight header budget there). Web's "Launching soon in all other major cities" banner was removed this pass (its `.coming-soon-banner` CSS removed with it).
   - **Native mobile**: fixed-height panel, its own scrollable list, not draggable (`src/components/BottomSheet.tsx` was removed when this changed — see git history, not this file). Unchanged this pass.
   - **Web desktop, tablet (both orientations), and phone landscape** (landscape joined this group this pass — previously it used the mobile bottom sheet, see below): the list floats as a side panel over the map (map renders full width behind it, not squeezed), each with its own tuned width in `web/src/styles.css` (desktop 340px fixed; tablet `clamp(340px, 38vw, 460px)`; phone landscape `clamp(230px, 42vw, 320px)`, scoped to `(hover: none) and (pointer: coarse) and (max-height: 500px) and (orientation: landscape)`). Selecting a listing shows its details via the map's own popup instead of a pinned card in the side panel (see "the selected-listing popup" under the web map bullet in Stack, above) — the side panel here is purely the scrollable list.
   - **Web mobile portrait only**: a two-mode **MAP / LIST** system (`web/src/App.tsx` — `sheetState: 'map' | 'list'`, `computeSheetSnaps`, the `handleSheetDrag*` functions; CSS scoped to `(max-width: 720px) and (orientation: portrait)`, driven by a `--sheet-h` custom property on `.map-frame`; the JS/CSS query is `MOBILE_PORTRAIT_QUERY`/`isMobilePortrait`, not the old broader "is this mobile" check). MAP mode (default) shrinks the sheet to just its drag handle plus, if a listing is selected, a tiny compact card floating over the map — the map stays the dominant surface. LIST mode expands the sheet into a tall scrollable list with that same compact card pinned at its top. Dragging the handle (or a fast flick, >0.5px/ms) switches modes; selecting a listing never forces a mode change either way, and the list always filters out whichever listing is selected so it can't appear twice. This replaced an earlier 3-state (collapsed/partial/expanded) single bottom sheet that spanned every breakpoint.
   - **The compact card** (`ListingDetailModal.tsx`'s `compact` prop) is one component reused in two places: portrait's own bottom-sheet peek zone, and — with no distance shown, see below — the content of every other breakpoint's map popup. Deliberately non-scrolling: name, price, note, "posted X ago", distance (portrait only), vote, directions, and report all fit one dense layout by design; don't let it grow past what fits without scrolling.
   - **Distance** (new this pass, web only — mirrors native mobile's own `distanceKm` haversine formula in `src/screens/MapScreen.tsx`, ported rather than reimplemented into `web/src/lib/distance.ts`): `App.tsx` best-effort requests the browser's geolocation once on mount (silent no-op on denial/unavailability — same graceful "just don't show it" fallback native uses) and derives each listing's `distanceKm`. Shown only on mobile portrait — next to "posted X ago" on the compact card, and next to the vote count on each scrollable list row (both CSS-gated to the same portrait-only breakpoint) — desktop/tablet/landscape show neither, unchanged from before this pass.
   - **Pins** were redesigned this pass from a solid pink pill to a compact white/black/pink price tag with a small pointer tail (`.map-pin` in `web/src/styles.css`) — selected state fills solid pink. Native mobile's own pin styling is untouched.
2. **Browser back / edge-swipe returns to the map, not out of the site** (new this pass, web only — SPA had never touched the History API before, so any back-press while e.g. Add Listing was open just exited `beggarsmap.com` entirely). `App.tsx` pushes one `history` entry the moment any internal view opens (Add Listing, a selected listing, the Legal modal, or the About modal — tracked by one `hasOpenState` boolean), and a single `resetToHome()` is the one place that closes all of them, used by every close button *and* by the `popstate` handler. An `isPoppingRef` flag distinguishes "the browser is already closing this for us" from "the user closed it via a button," so the same history entry is never popped twice (double-popping was the exact bug that first surfaced while building this — it would land one press *past* home, back out on the real previous site). With nothing open, back/swipe behaves like normal browsing and correctly leaves the site.
3. **Map click only places a pin inside the explicit "pick a location" flow — never on a bare tap** (changed this pass, web only; native's own long-press-to-add, described next, is untouched). `handleMapClick` in `App.tsx` is now a no-op unless `pickingLocation` is already true (the user explicitly chose "Pick on map" or "Use current location" from inside the Add Listing modal first) — a bare click used to drop a candidate pin and offer "+ Add this place" regardless of context; that idle hint pill is gone along with it.
4. **Map-long-press-to-add** *(native mobile only now — see above for why web's raw-click equivalent was removed)* — long-pressing (`MapScreen.tsx`'s `handleMapLongPress`) an empty spot on the map starts Add Listing pre-filled with that location, skipping the separate picker step. Additive on top of the other entry points below, not a replacement for any of them.
5. **Add Listing** — name, price, photo, note, plus location entry points: current-location GPS, "Pick on map" (mobile: opens `PickLocationScreen`, a fixed center-pin over a pannable map with its own landmark search; web: hides the Add Listing modal — its in-progress fields stay intact — and hands off to the homepage's own full-screen `MapView`/click-and-search flow, reusing that single map instance instead of a second one, then restores the modal once confirmed or unchanged on Cancel), or paste a Google Maps link (`googleMapsLink.ts` parses both full links and short `maps.app.goo.gl` links, resolving the redirect first). Every submission runs through a lightweight **content-moderation heuristic** (`contentModeration.ts`, duplicated per-platform, identical keyword-blocklist logic): a non-food keyword list (`cloth`, `salon`, `pharmacy`, `real estate`, etc.) rejects obviously non-food listings before insert — not an LLM call, just a substring match against name+note.
6. **Photo upload — single on mobile, multi on web, and web's is currently broken in production.** Mobile (`AddListingScreen.tsx`) supports exactly one photo, uploaded to the `listing-photos` bucket at `${userId}/${timestamp}.${ext}`, stored as `listings.photo_url`. Web (`AddListingModal.tsx`) supports up to 4 photos (`MAX_PHOTOS = 4`), writing photos beyond the first into the `listing_photos` table (`0009`) — **but that table is confirmed not applied in production** (see Deployment status above), so today a real web user adding a 2nd+ photo gets a failed insert. Independently of that, **the display side never caught up either**: `ListingDetailModal.tsx` and the web list card both still only render `listing.photo_url` (photo #1), so even once `0009` is deployed, photos 2–4 would be stored but still not shown anywhere. Fix the missing migration and finish the display side (or cap upload back to 1) before treating multi-photo as a real, working feature.
7. **Listing Detail** — photo, vote button, Directions handoff (device's native maps app, no in-app turn-by-turn), report flow (4 fixed reasons — "Closed / doesn't exist", "Wrong price", "Inappropriate photo", "Spam or duplicate" — insert into `reports`, deduped per user+listing+reason by `0007`).
8. **Reviews are fully removed from the UI on both platforms** (`StarRating.tsx` deleted from both `src/components/` and `web/src/components/`) **but the backend schema is intentionally retained for possible future use** — do not drop `reviews`/`listing_ratings`/their RLS policies without being explicitly asked. The current live quality signal is vote-only: a single upvote per user per listing (`votes` table, "▲ Worth it (N)" toggle button, no downvote — deliberately matches Geoji Map's own upvote-only model; a bad-but-not-broken listing just doesn't accumulate votes, a genuinely broken one goes through Report instead). The `Review`/`ListingRating` TypeScript types (both platforms) and the unused `.review-*`/`.star-*` CSS rules (web) were removed as dead code in an earlier pass. The mobile Leaderboard no longer displays a "review count" for the same reason (see below).
9. **Leaderboard** *(mobile only — web has no equivalent)* — reads the `leaderboard` view, ranked by `score` (`listing_count + review_count`, the latter now permanently 0 for any future contributor since nothing can create a `reviews` row anymore — display of `review_count` was removed from the UI, but the view's own score formula is schema and was intentionally left untouched).
10. **Profile** *(mobile only — web has no equivalent)* — my contributions + rank, sign out, and "Delete my account" (see Account deletion above). No settings/bio.
11. **Legal** — Privacy Policy & Terms, reachable from Profile (mobile) or a footer link (web); web's copy explicitly states the site is anonymous with no accounts, matching the anonymous-auth decision above.
12. **About** — `AboutContent.tsx` (web, shared between a desktop/tablet sidebar panel and a mobile-only modal opened via the "About Us" button) / an `AboutSection` in mobile's `ProfileScreen.tsx`. **Logo treatment changed this pass**: the mark (`Logo.tsx`'s "B") plus a "Beggars Map" wordmark now lead the content as `.about-logo-block`, replacing the old plain-text `<h1>` header — but the sidebar hides that whole block (`.about-panel .about-logo-block { display: none }`, since the topbar's own "B + Beggars Map" is already visible right above it on every desktop/tablet view) and the wordmark span is hidden unconditionally (`.about-logo-word { display: none }`), so in practice only the mobile modal shows the bare B mark, and the desktop/tablet sidebar shows no logo at all. Footer on web links to app-store pages (both still "Coming soon").

## Known limitations / remaining technical debt
- **Web has no Profile, no Leaderboard, and no self-service account deletion.** Its contribute/vote/report flows work anonymously, but there's currently no way for a web visitor to see their own contributions, their rank, or delete their data short of contacting the site owner directly. Worth deciding whether this gap is intentional-for-now or needs closing before wider launch.
- **Web multi-photo upload/display mismatch** (see "Photo upload" above) — data is being collected with no consumer.

## Conventions
- Browsing is open with no login on both platforms; mobile requires Google sign-in to post/vote, web is silently anonymous for everyone (see Auth above — these are genuinely different, not a simplification).
- Every listing needs a report/block affordance (required by both app stores for UGC).
- No submission gate on listings — keep friction near zero, quality comes from community upvotes; the content-moderation keyword check is the only automatic gate.
- `npm install` in this repo needs `--ignore-scripts` — a user-level `.npmrc` (`allow-scripts=@anthropic-ai/claude-code`) blocks project-scoped install scripts otherwise. This also breaks `npx expo install`, `npx expo install --fix`, and EAS's auto-install-missing-package step; install the specific version directly via `npm install --ignore-scripts <pkg>@<version>` (check `node_modules/expo/bundledNativeModules.json` for the version this SDK expects), then re-run the command that wanted it.
- After any mobile change, verify with `npx tsc --noEmit` and `npx expo export --platform android` (then `rm -rf dist`) before calling it done — this catches native-module/bundling breakage that a typecheck alone won't. For web, `npx tsc --noEmit` (or `npm run build` in `web/`, which runs `tsc -b && vite build`) — both currently pass clean.
- The user's dev phone (Android) can't reach this PC over their normal Wi-Fi/hotspot setup (a known Android hotspot NAT quirk blocks the host phone from reaching its own hotspot clients) — `npx expo start --tunnel` is the reliable way to connect the dev-client to Metro, not a plain LAN `npx expo start`.
